# The software factory: notes on Web Dev Cody's talk

**Video:** "You Shouldn't Be Coding Anymore. You Should Be Building a Factory." by Web Dev Cody, published 2026-11-05, 17:10 long.
https://www.youtube.com/watch?v=nwMNQJ_Wtw8

**How this note was made (2026-11-12, Slate):** Gemini watched the video (audio and frames), and I read the full YouTube captions alongside it. The quotes and claims below come from the captions. Timestamps come from Gemini and are approximate.

## The idea in one paragraph

The old pipeline (user → product owner → designer → engineer → deploy → fix) gives way to a "software factory". Everyone prompts the factory directly. It runs each task in an isolated sandbox with a model that works for hours unattended, and it returns a pull request. Humans sit only at the edges: requirements on the way in, review on the way out. The engineering job moves from writing code to tuning the factory: its skills, its knowledge base, its triggers and its merge rules.

## What the factory contains (as drawn in the talk)

- **Sandbox.** Isolated, so it is safe to let the model run long.
- **Skills and workflows.** Separate plan, implement and code-review skills, with sub-agents reviewing in parallel. "It's not just passing your prompt to Opus and saying good luck."
- **Knowledge base and context.** Business context from meetings, Slack and Teams, pulled in through MCP or stored in the knowledge base.
- **Triggers.** Cron jobs, Slack messages and external events. Examples: daily sweeps that improve performance or security, clean up code and update docs.
- **A self-improvement loop.** A skill reads the session logs and opens a PR that improves the skills themselves. He credits Matt Pocock's `retro` skill for this.

## Key points with timestamps

1. **(~02:30) Non-engineers ship.** At his company, product owners land features without going through a designer or engineer, and designers open PRs that change UIs. Engineers review.
2. **(~05:10) Humans in the loop live at the edges.** On the way in: prompting and gathering requirements. On the way out: reviewing code, screenshots and metrics.
3. **(~04:00) The PR description carries the review.** For real products it should state how the architecture changed, the risks, a security analysis, performance metrics and the effect on third-party integrations. His game PR (#702, a Blender-built jack-o'-lantern) lists triangle count against a cap, the animations tested, and "no client/server state changes".
4. **(~06:35) The factory is company-specific.** "You can't just reuse the exact same skills" across companies. Someone has to own and refine them.
5. **(~11:30) Auto-merge by a stated gate.** Example rule: merge if it is certified not to cost more than 1–2 FPS or to add render-loop milliseconds. Low-risk PRs merge without a human. High-risk ones (an API contract change, an auth change) still get a human reviewer. The PR's risk section is what the merging agent reads.
6. **(~13:16) His own practice.** On side projects he no longer reviews PRs by hand. He tells an agent "fix conflicts, address comments, merge when done", often on a cron. On work projects he still reads the code.
7. **(~14:11) Speed against security is the open question.** "How many more tokens do you want to throw at the pull request" before trusting a merge with no human review.
8. **(~15:25) The real bottleneck is understanding.** You need to understand user needs and the external systems you integrate with. "If you just keep on throwing as much context as possible to Opus, it still gets a little bit confused." Curated context beats more context.

## How it maps to what we already run

We already run most of this, so the talk is more useful as a checklist than as news.

| Talk | Us | Gap worth looking at |
|---|---|---|
| Factory, sandboxes, PRs | Crew colours, worktrees, sub-agents, PRs | None in shape |
| Skills plus a `retro` self-improvement loop | Vendored Matt Pocock skills, `retro`, memory files | Retro runs only when an agent decides to. Nothing reads session logs on a schedule and proposes skill PRs. |
| Knowledge base from meetings and chat | Memory, Obsidian board, Granola/Pumble access | Lessons are scattered across one memory index per agent (one is already over its size limit) |
| Triggers and daily sweeps | Crons, scheduled checks | No standing performance/security/docs sweep on Zoomies |
| Auto-merge by stated gate | The kitchen self-merges. Zoomies uses roster reviewers. | Zoomies PRs carry no machine-readable risk section. A "low-risk = auto-merge" rule would need one first. |
| Humans at the edges | Bogdan decides product and copy, and gives the "prod" word | Matches |

One lesson from our own records applies to his auto-merge gate. A gate that a model "certifies" is the model's own verdict (see our ZSP-931 lesson: regenerated LLM test plans produced two false FAILs). The FPS gate should be a measured number from a script, never a sentence in the PR.

## Claims to treat with care

- **"Anthropic … may train on that" (~10:09).** This is the speaker's claim. Anthropic's published commercial and API terms say customer data is not used for training by default. I have not re-checked the current terms today, so check them before quoting either side. His underlying point still holds: piping production databases and every meeting transcript into any third-party sandbox is a data-governance decision.
- **"Railway … OpenCode also got hacked", distillation attacks (~14:11).** Named in passing with no detail. Not verified.
- **Model naming.** The captions say "Opus 5.5 and Astra", which matches the current models. Gemini's summary misheard this as "Opus 3.5". The captions are right.

## Ideas we could act on

1. A weekly trigger that reads agent session logs and opens PRs that improve skills, i.e. his feedback loop made scheduled.
2. A standard **Risk** section in Zoomies PR bodies (architecture, security, performance, external impact). It helps human reviewers today and makes any future auto-merge rule possible.
3. Only consider auto-merge for a class of PR whose gate is a measured check (tests, bundle size, a perf script), never a model's own say-so.
