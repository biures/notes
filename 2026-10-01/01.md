# handoff-spec: the Opus skill that writes a spec a cheaper model can execute

Run on the strong model. It investigates the codebase, makes every decision, writes the risky code verbatim, and produces a spec where every step verifies itself. The same skill has a `verify` mode for reviewing the cheaper model's diff and report afterwards. The frontmatter pins `model: opus`, so it runs on Opus even from a Sonnet session.

# Handoff spec — do all the thinking here, so the implementer never has to

The spec you write is executed literally by a cheaper model. Every decision you leave open becomes a guess made by a weaker model, and that guess is where the result stops matching yours. So: investigate deeply, decide everything, write the risky code yourself, make every step self-verifying, and keep the whole thing short enough for a small context window.

## Modes

- `/handoff-spec <task description or ticket>` writes `specs/<slug>.md` (create `specs/` if absent; use a path the user gives instead if they give one).
- `/handoff-spec verify <spec path>` reviews what the implementer did. See "verify mode" at the end.

## Phase 1 — Investigate before writing a word of the spec

1. Read the code the task touches end to end: entry points, callers, the tests that cover it. Record exact `path:line` for everything you will refer to.
2. Run the checks that will be the verification (test suite, typecheck, lint, build) and record the baseline: what is green and what is already red before any change. A pre-existing red must be named in the spec or the implementer will chase it.
3. Find the pattern to copy for each kind of change: the nearest similar feature, the test style, the error style, the naming convention. Note `path:line`.
4. List every decision the task implies and make each one now: names, where code lives, API and data shapes, error behaviour, edge cases, migrations, flags, defaults, what happens on failure. If a decision genuinely belongs to the user, ask the user now, in one list. Never leave a decision to the implementer.
5. Mark the risky parts: concurrency, tricky algorithms, subtle API semantics, security checks, data migrations, anything you would expect a junior to get wrong or a weaker model to "simplify". You will write that code verbatim in the spec. The implementer places it; it does not author it.
6. Decide the step order by dependency and the step size by risk: the hardest parts get the smallest steps.

## Phase 2 — Write the spec

Rules that make a spec executable by a weaker model:

- Decisions, not options. The words `consider`, `as appropriate`, `as needed`, `e.g.`, `etc.`, `or similar`, `should probably`, `might`, `ideally` do not appear. Every identifier is named. Every path is exact.
- Risky code is written out in full, final form, in a code block. Everything else is described precisely enough that only one implementation satisfies it.
- Every step carries its own verification: a command and the exact expected output or assertion. A step without a check is not a step.
- Fallbacks are pre-authorized or absent. "If the test still fails because of X, do Y" is allowed. Anything not pre-authorized means the implementer stops and reports. Say that in the spec.
- Say what must not be touched, and why, so the implementer does not "improve" it.
- Put the must-know facts first. The implementer has a smaller context; do not paste large existing code, point at `path:line` instead, except for the risky code you wrote.
- Define done as commands with expected results, never as adjectives.

## Spec template

```
# <Task title>

Spec for /handoff-implement · written by <model> on <date>
Baseline before changes: `<check command>` → <exact result, including any pre-existing red>

## Goal
<2 to 4 sentences: what changes for the user or the system. No implementation words.>

## Decisions already made
- <decision> — <why>. The implementer must not re-decide these.
- ...

## Files to touch
- <exact path> — <what changes, one line>

## Do not touch
- <exact path or area> — <why>

## Context the implementer needs
- Pattern to copy for <thing>: <path:line>
- Convention: <rule, with an example path>
- How to run things: <commands>
- Gotchas: <the trap and how to avoid it>

## Steps
### Step 1 — <title> (file: <path>)
Change: <precise description, or the verbatim code block>
Verify: `<command>` → expect: <exact output or assertion>
If it fails: <pre-authorized fallback> | STOP and report

### Step 2 — ...

## Acceptance
Run all at the end, in this order:
- `<command>` → expect: <result>
- ...

## Report back (the implementer fills this)
- Steps completed, each with its Verify output
- Deviations (what the spec said, what was found, what was done)
- `git diff --stat`
- Open questions
```

## Self-check before handing off

Every line must be true, or the spec is not ready:

- A literal-minded junior could execute it without asking a single question.
- `grep -nE "consider|appropriate|as needed|etc\.|e\.g\.|or similar|should probably|might|ideally" specs/<slug>.md` returns nothing.
- Every step has a Verify line with an expected result.
- Every new name (function, file, flag, env var, test name, error message) appears in the spec.
- The risky parts are written out as code, not described.
- Nothing in it requires knowledge the implementer cannot read from the repo or the spec.
- The spec is as short as it can be while complete.

Then tell the user: the spec path, the model to run it on, and the two commands (`/model <cheaper>` then `/handoff-implement specs/<slug>.md`), and that you will run `/handoff-spec verify` afterwards.

## verify mode

Input: the spec, the implementer's Report back, and `git diff` against the starting commit. Check, in this order:

1. The diff touches only "Files to touch". Anything else is a finding.
2. Every step has Verify evidence in the report, and the evidence matches the expected result literally.
3. No forbidden moves: a deleted, skipped or weakened test or assertion; `any`, `@ts-ignore`, broad `catch {}`, `eslint-disable`, `--no-verify`; a new dependency; a config change not in the spec.
4. Re-run the Acceptance commands yourself. Do not trust pasted output for these.
5. Every "Decisions already made" is honoured in the code.
6. Read the diff once as a reviewer would: does the code do what the spec says, not merely pass the checks?

Output either `PASS` with the acceptance outputs, or a numbered fix list in the same Step format (Change / Verify / If it fails), which the implementer runs with `/handoff-implement <spec> --fixes`. Keep the fix list small and verifiable; if the fixes amount to a redesign, rewrite the relevant steps of the spec instead.
