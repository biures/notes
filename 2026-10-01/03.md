# Handoff workflow for Claude Code and GitHub Copilot CLI: Opus writes the spec, Sonnet implements, Opus verifies

Two skills that keep the expensive model for judgment only. `handoff-spec` and `handoff-implement` are the other two notes of today; this one is how to install and run them in both tools, and why the result holds up against an end-to-end Opus run.

Both skills are plain Agent Skills (`SKILL.md` with `name`, `description`, `compatibility` only), so one file serves both tools. Neither tool lets a skill switch the model, so the model switch is a step in the loop, and each skill opens with a model guard that stops and tells you to switch if it finds the wrong class of model.

## Install

Claude Code reads `~/.claude/skills/<name>/SKILL.md`; Copilot CLI reads `~/.copilot/skills/<name>/SKILL.md` (or `~/.agents/skills`). Both read `.github/skills/<name>/SKILL.md` and `.claude/skills/<name>/SKILL.md` inside a repository, which is the better place at work so the whole team gets them.

```sh
# personal, both tools, one copy each (paste each SKILL.md from the companion notes)
mkdir -p ~/.claude/skills/handoff-spec ~/.claude/skills/handoff-implement
mkdir -p ~/.copilot/skills
ln -s ~/.claude/skills/handoff-spec ~/.copilot/skills/handoff-spec
ln -s ~/.claude/skills/handoff-implement ~/.copilot/skills/handoff-implement
```

In a Copilot CLI session, `/skills reload` then `/skills info handoff-spec` confirms it loaded. Copilot also exposes `copilot skill list|add|remove|enable|disable` from the terminal.

## The loop

Claude Code:

```
/model opus
/handoff-spec <task, ticket text, or "see JIRA-123">      # investigates, decides, writes specs/<slug>.md
/model sonnet
/handoff-implement specs/<slug>.md                       # executes, verifies each step, reports
/model opus
/handoff-spec verify specs/<slug>.md                     # diff + report against the spec → PASS or a fix list
/model sonnet
/handoff-implement specs/<slug>.md fixes                 # runs the fix list the same way
```

Copilot CLI, interactive: the same four prompts, switching with `/model` and picking Claude Opus 5 or Claude Sonnet 5 from the list (the list shows each model's cost next to it). The skill is invoked by naming it with a slash in the prompt, for example `Use the /handoff-implement skill on specs/<slug>.md`.

Copilot CLI, one command per phase (good for the implementation, which needs no supervision once the spec is right):

```sh
copilot --model=claude-sonnet-5 --prompt "Use the /handoff-implement skill on specs/<slug>.md"
```

Add the permission flag your CLI version documents for unattended tool use (`copilot help`); in a session it is `/allow-all`. `COPILOT_MODEL=claude-sonnet-5` in the environment does the same as `--model`.

Run the verify step after `/compact`, or in a fresh session, when the implementation turn was long. Verify mode needs only the spec, the report and `git diff`, so the Opus input stays small.

Decision rule for which tasks to hand off: if you can write "done" as commands with expected outputs before starting, hand it off. If the design will only emerge while coding (exploration, unclear requirements, a spike), use Opus end to end; a spec written without the answers would move the guessing to the weaker model, which is the one thing this loop exists to prevent.

## Optional: pin the model in a custom agent

Skills cannot carry a model, but custom agents can. Copilot CLI reads `~/.copilot/agents/<name>.agent.md` (repository: `.github/agents/`), with `description` required and an optional `model` property ("model to use when this custom agent executes; if unset, inherits the default"). Two thin agents turn each phase into one command:

```markdown
---
name: handoff-implement
description: Executes a handoff-spec spec on the cheaper model; returns the Report back section.
model: claude-sonnet-5
tools: [read, edit, execute, search]
---
Use the /handoff-implement skill on the spec path in the prompt. Return only the filled "Report back" section.
```

```sh
copilot --agent=handoff-implement --prompt "specs/<slug>.md"
```

The docs state the property for the cloud agent and the IDEs; whether your Copilot CLI version honours it is a thing to check once, by reading the model name shown above the input box after `/agent`. If it does not, `--model=` on the command line is the guaranteed lever. Claude Code has the same shape with `.claude/agents/<name>.md` and `model: sonnet`, and there the field is documented for the CLI, with precedence over the session model.

## Why the result matches an end-to-end Opus run

The cheaper model diverges in five known ways. Each one has a counter built into the prompts:

1. **It guesses at ambiguity.** The spec forbids every open decision: names, shapes, defaults, failure behaviour are all decided by Opus, and the spec skill greps its own output for hedge words before handing off.
2. **It writes weaker code where the problem is hard.** Opus writes the risky code verbatim into the spec. The implementer places it; it does not author it.
3. **It drifts: refactors "while here", touches extra files, adds a dependency.** The implementer has an explicit forbidden-moves list and a files-to-touch list; verify mode fails the diff on anything outside it.
4. **It declares done without proof, or makes a check pass by weakening it.** Every step carries a Verify command with an exact expected result; a red step stops the run; deleting or weakening a test is forbidden by name; verify mode re-runs the acceptance commands itself.
5. **It works around a mismatch instead of reporting it.** Any disagreement between spec and reality is a Deviation report and a stop, except a fallback Opus pre-authorized in that step.

What this does not cover: a wrong decision by Opus in the spec is reproduced faithfully by the implementer. That is the same risk as the end-to-end run, and verify mode's last check ("does the code do what the spec says, not merely pass") is where it surfaces.

## Cost shape

Copilot bills usage per token since June 2026 (list prices per million tokens, input/output): Claude Opus 5 $5/$25, Claude Sonnet 5 $2/$10, Claude Haiku 4.5 $1/$5, so Sonnet is 2.5 times cheaper than Opus 5 per token. Organizations still on the legacy request-based annual plans pay per prompt times a model multiplier, where the gap is far larger (legacy table: Opus 4.8 at 27, Sonnet 4.6 at 9, Haiku 4.5 at 0.33). Opus pays for the investigation, the spec and the verify pass; Sonnet pays for the implementation turns, which are most of the output tokens and all of the tool churn. Measure it with `/usage` in Copilot CLI or `/cost` in Claude Code on three real tasks before trusting any ratio.
