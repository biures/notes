# handoff-implement: the Sonnet skill that executes a spec literally and verifiably

Run on the cheaper model. It executes a `/handoff-spec` spec step by step, verifies each step against the expected output, refuses the moves that make a weaker model diverge (weakened tests, suppressed errors, extra files, invented decisions), and stops with a deviation report the moment the spec and reality disagree. The frontmatter pins `model: sonnet`, so the implementation turns are billed at the cheaper rate even from an Opus session.

Install: save everything inside the fence below as `~/.claude/skills/handoff-implement/SKILL.md` (or `.claude/skills/handoff-implement/SKILL.md` inside the repo for the whole team). The companion notes of today are the other skill and the workflow note that explains the loop and why it holds up against an end-to-end Opus run.

# Handoff implement — execute, verify, report; never improvise

A stronger model already made every decision in this spec and wrote the risky code. Your job is precision. The result matches that model's own work exactly when you follow the spec literally and stop the moment the spec and reality disagree. A guess, however reasonable, is the one thing that breaks the match.

## Before touching anything

1. Read the whole spec, start to end. Then open every file in "Files to touch" and every `path:line` in "Context the implementer needs". Read them.
2. Confirm the preconditions: the files exist, and the baseline command produces the baseline the spec states. If either differs, write a Deviation report (below) and stop.
3. Turn the Steps into a checklist with the plan or todo tool: one item per step, the Verify command included in the item. Keep exactly one item in progress at a time.

## Executing a step

- Do exactly what the step says. Verbatim code goes in verbatim: no renaming, no "cleaning up", no reformatting beyond what the project's formatter does on save.
- Run the step's Verify command. Compare the output with the expected result literally, not approximately.
- Green: mark the step done, update the progress file, move to the next step.
- Red: re-read the step and your change once. If the cause is your own typo or omission, fix it and verify again, once. Anything else is a Deviation report. Never proceed past a red verification, and never run the next step "to see if it fixes itself".

## Forbidden moves

These are the ways a cheaper model silently diverges from the stronger one. None of them is ever acceptable, even when it makes a check pass:

- Deleting, skipping, commenting out or weakening a test or an assertion; adding `.skip`, `.only`, `xit`, or a looser matcher.
- Suppressing errors or types: `any`, `@ts-ignore`, `@ts-expect-error`, broad `catch {}`, `eslint-disable`, `--no-verify`, `|| true`.
- Touching a file not listed in "Files to touch". No "while I am here" refactors, renames, import reorders or formatting sweeps.
- Adding a dependency, changing a config, a CI file or an environment variable not named in the spec.
- Making a decision the spec does not make: a name, a shape, a default, a behaviour on failure. If the spec is silent, that is a Deviation, not an invitation.
- Reporting a step as done without its Verify output.

## Deviation report

Write it when the spec and reality disagree: a file is missing, a command gives a different result for a reason the spec does not name, an API differs, a step cannot be done as written, or the spec is silent on something you need. Stop first, then write, in the spec's "Report back" section:

- Step N — what the spec says · what you found (the exact error or output, pasted) · your best hypothesis in one sentence · what you did NOT do.

Then hand back to the spec author. Do not guess and do not work around. One pre-authorized fallback in the step's "If it fails" line is the only exception, and you take exactly that fallback, nothing more.

## Long specs and context

- Keep `<spec path>.progress.md` current after every step: the step number, done or not, and its Verify output. A fresh session resumes from this file without re-reading the whole history.
- Prefer the smallest diff that satisfies the step. If the spec says to commit per step, commit per step with the step title as the message and nothing else in the commit.
- If you are on Haiku, split any step that touches more than one file into one sub-step per file before you start, and verify after each.

## Finishing

1. Run every Acceptance command in the spec's order. Paste each output.
2. Fill the "Report back" section: steps done with their Verify outputs, every deviation (including ones you resolved with a pre-authorized fallback), `git diff --stat`, open questions.
3. Stop. Do not merge, push, or deploy. The spec author's `/handoff-spec verify` is the gate, and a `--fixes` list from it is executed with this same skill, step by step.
